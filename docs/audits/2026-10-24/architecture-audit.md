## Architecture invariants that should govern issue triage

1. Preserve separate 2D millisecond atlas timing, integer production frames with rational rates, and rig floating-point seconds; conversion must be explicit.
2. Canonical rig 3D coordinates are right-handed +Y up, +Z forward, meters and XYZW quaternions. New scene/camera/physics adapters must conform or explicitly convert.
3. Existing acquisition claim/token, kernel locks, review store and source transport remain authoritative. New Director and library components must reuse them, not invent competing controllers or approval stores.
4. Classify evidence independently: implemented code, passed current tests, retained historical independent verification, actual visual review, production approval, and supported integration are different facts.
5. Source image hash, normalized raster hash, logical actor identity, rig revision and content digest are distinct identities. Equal bytes do not make actors interchangeable.

## Security observations from source inspection

`hatch.py` uses argv subprocess calls rather than shell interpolation, local kernel locking, journaled state and staged writes. `asset_contracts.py` rejects unsupported/animated source formats before decoding and bounds bytes/pixels/frame counts/work estimates. `production_sources.py` rejects noncanonical paths, reserved Windows names, case/Unicode aliases, duplicate keys and transport oversize. `atomic_publish.py` uses Windows exclusive rename or Linux/macOS no-replace native operations and fails closed on unsupported platforms. `production_workflow.py` locks bound and unbound acquisition runs before archive creation and rejects active claims. `rig_http.py` binds 127.0.0.1, uses constant-time bearer comparison, rejects foreign origins, bounds request size/time and limits operation concurrency. These are observed controls, not proof against all races or resource attacks.

No demonstrated new exploitable vulnerability is alleged here. Root `hatch.py:read` still uses ordinary unbounded `json.loads`, unlike newer strict boundary loaders; decide hardening only after identifying which files are untrusted inputs and whether existing issue scope already covers it. Avoid a generic duplicate security backlog.
